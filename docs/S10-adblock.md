# 10단계 광고 차단 측정과 결과 (spec 6.7)

2026-11-11

## 1. 모든 요청을 호스트로 보낼 때의 로딩 시간

탭의 모든 요청에 `WebResourceRequested` 필터("*", 모든 종류)를 걸어 호스트 처리기를 거치게 한 경우(켬)와 걸지 않은 경우(끔)를 비교했다. 사이트 6곳, 켬·끔을 번갈아 3번씩, `loadEventEnd` 기준(ms).

| 사이트 | 끔 (가운데 값) | 켬 (가운데 값) |
| --- | --- | --- |
| naver.com | 148 | 102 |
| namu.wiki 대문 | 1,522 | 773 |
| youtube.com | 726 | 672 |
| gall.dcinside.com 목록 | 453 | 281 |
| yna.co.kr | 905 | 682 |
| theverge.com | 1,140 | 1,258 |

- 켬이 대부분 오히려 빨랐다. 순서와 캐시, 네트워크 흔들림이 차이를 만든 것으로 본다. 호스트를 거치는 비용은 이 흔들림보다 작아 보이지 않는다.
- theverge 켬 한 번은 22.5초가 걸렸는데, 같은 조건의 다른 두 번은 1초 남짓이라 네트워크가 멈춘 것으로 본다.
- 엔진 검사는 요청 하나에 마이크로초 단위라 더하지 않았다.
- 결론: spec 6.7의 방식(모든 요청을 호스트에서 검사)대로 만든다.

## 3. 보완 (남은 문제 셋)

| 확인 | 결과 |
| --- | --- |
| 서비스 워커가 `fetch()`로 받는 광고 스크립트 (로컬 시험 페이지) | 사이트 켬: `Failed to fetch`로 막힘, 사이트 끔: 200. **기존 필터(요청 출처 ALL)로 이미 막힌다.** 0단계 9번 결과와 다르다(그때는 처리기가 불리지 않았다) |
| 스크립틀릿 자원 | uBlock Origin 1.75.4 스크립틀릿 151개(이 중 trusted 33개)를 만드는 데 1초쯤. Brave 자원 17개도 함께 |
| 유튜브 영상 페이지 | 스크립틀릿 적용, `ytInitialPlayerResponse`의 `adPlacements`·`playerAds`·`adSlots`가 지워짐(끄기 전에는 있었다). 영상은 정상 재생 |
| 광고 틀 (`click.alibaba.com`, `$subdocument` 규칙) | 틀 문서가 막힘(막은 개수 1) |
| 틀 안 화면 숨기기 (다른 출처 틀 안의 `.abovead`) | 맨 위와 틀 안 모두 숨겨짐. 사이트를 끄면 둘 다 보임 |
| 실제 사이트 | yna.co.kr 12개, gall.dcinside.com 11개, youtube.com 8개 막음. 디시 글 목록 정상 |

- EasyList는 `127.0.0.1`과 `localhost`에서 일반 숨기기를 일부러 끈다(`@@://127.0.0.1$generichide`). 로컬 시험은 `127-0-0-1.nip.io`로 했다.
- 사이트별 끄기는 틀이 아니라 탭의 맨 위 사이트를 따른다.

## 4. 한계

- **서비스 워커의 Cache Storage**에서 바로 내는 응답은 네트워크로 가지 않으니 막지 못한다.
- **스크립틀릿**은 맨 위 문서에만 넣는다.
- 스크립틀릿 판(1.75.4)은 앱에 정해 두었다. 올리려면 앱을 새로 낸다. 규칙(uBlock filters)은 하루에 한 번 새로 받는다.
